# Ordinary-task storage (#7)

Implements the ordinary-task subset of the [full contract](data-model.md) in existing shared Room schema 3. Engineer technical choices on 2026-10-12 use the owner's routine-choice delegation, preserving settled [behavior](behavior.md). Tasks have id/listId/title/scheduledDate/priority/shortNote/reminderTime/completedAt/completionDate/createdAt/updatedAt. Recurrence triplet/override columns wait for #12, where actual template ownership exists; this API accepts no series/slot/override fields.

`DatabaseProvider.getTaskRepository()` uses the same opened database as Settings/lists. The internal DAO persists rows; public repository operations run on worker threads, with create/update/completion/delete in Room transactions. IDs are UUID v4, checked against both implemented lists and tasks under the same transaction; ListRepository creation now checks both too. Create defaults to the stable default flag's list ID, Medium priority, no date/note/reminder/completion. `TaskContent` contains editable content; `Task.content()` produces it from an existing row. Update preserves ID/creation and completion fields; only successful changed content/state advances update time to max(previous, injected clock), while unchanged saves retain it. Clock correction never falsifies a captured completion instant.

Shared text validation rejects unpaired surrogates; titles/list names trim the exact Unicode White_Space set from edges and reject blank results. Internal spaces, accents, Cyrillic, emoji and note whitespace remain unchanged. Nullable short notes and empty strings stay distinct. Priorities are exactly high/medium/low. `LocalDate`/`LocalTime` ensure actual Gregorian dates/clock times; repository validation further requires date years 0001–9999 and minute precision (no seconds/nanos). Dates store TEXT `YYYY-MM-DD`, times `HH:mm`, instants INTEGER epoch milliseconds within the contract's year range. Dates never convert through timezone/UTC midnight. No placeholder search shadows are stored; #26 still owns full Unicode search integration.

TaskContent updates must be internally valid, including no requested reminder without a date. To remove a date use `setScheduledDate(id, null)`, which clears both date and the existing reminder atomically; updating with a complete content object also works when both are null. Example: task dated Oct 12 at 09:05 becomes undated/no reminder, with ID/note/completion preserved. Changing its non-null date retains the selected minute time. These are requested metadata only; no alarms/delivery/cancellation guarantee is introduced.

`complete(id)` captures one millisecond instant and its local calendar day using an injectable current-device ZoneId in one transaction; repeated completion is unchanged. `reopen(id)` clears both fields together. `setCompletion(id, instant?, capturedDay?)` supports explicit storage-state writes with strict pairing/range/precision validation. Issue #8 now integrates the transactional parent/child gate and automatic reopen described below; completed-day view policy remains #11. Unrelated content edits retain the saved completion day even after timezone travel. Example: capture Oct 12 in UTC+14, then move to UTC-12 and edit priority: captured Oct 12 remains, rather than being recomputed from the instant.

`active()` and `completed()` are Room `Flow<List<Task>>` queries partitioned by null/non-null stored completion instant. They return all records, ordered by stable ID for deterministic storage results, with ongoing invalidation after persisted writes. There is no priority/date-view filtering, completed-today crossing-out, Log eligibility or automatic history deletion; #10/#11 implement those policies. Public calls return persisted Task values; deletion returns Unit. Unknown read/update/delete IDs raise NoSuchElementException; invalid content/list IDs/pairs raise IllegalArgumentException; SQLite errors propagate and transactions roll back. Structurally impossible date/time input fails during standard Java-time construction/parsing before mutation.

Issue #10 now adds pure [date/list filtering and priority ordering](task-10-validation.md) with explicit Clock and the shared completion-eligibility boundary. Its `viewCandidates()` query includes all stored unfinished/completed tasks so same-day completed records are retained for those results; the original storage partition queries remain unchanged. #11 still owns completion-day view/history orchestration.

Task.listId has a real Room/SQLite FK to lists.id with ON DELETE RESTRICT and an index. ListRepository custom-list deletion now deletes every ordinary task in that list, including completion metadata/short notes, before removing the list and compacting surviving positions in one transaction. A failure after task deletion rolls back tasks/list/order. Renamed default-list deletion remains prohibited. Subtask cascades/gates are integrated by #8; templates/overrides/exclusions including moved occurrences (#12), confirmation/screens (#21/#27/#17), and reminder safety/cancellation/LocalWork (#28/#30/#33) remain mandatory integrations before their features are exposed. No fictitious dependent tables or no-op handlers are added.

Explicit 2-to-3 migration creates tasks/FK/index, idempotently retains the existing list-default triggers, and never rewrites Settings/list values. Registered 1-to-2-to-3 path and historical generated schemas 1/2 remain; generated schema 3 is tracked. MigrationTestHelper uses actual exported schema 2 plus representative Settings/default/custom-list rows and validates Room schema 3; checks confirm unchanged rows through subsequent task writes/reopen. Existing version-1 upgrade tests also proceed through the current registered path.

Necessary compatibility dependencies are pinned: Java-time [core desugaring](https://developer.android.com/studio/write/java8-support) with [desugar_jdk_libs 2.1.5](https://github.com/google/desugar_jdk_libs/blob/master/CHANGELOG.md), whose 2.1 line requires AGP 8+ (existing AGP 9.0.1 qualifies), retains minSdk 23. [Coroutines Android 1.10.2](https://github.com/Kotlin/kotlinx.coroutines/releases/tag/1.10.2) supplies the explicit Flow/collector runtime; Room's existing coroutine integration performs database invalidation. No additional architecture/plugin/module or UI dependency is added. Actual API36 evidence and limits are in [validation](task-7-validation.md); general failure/version policy remains [the foundation](storage-foundation.md).

## Ordinary checklists in schema 4 (#8)

Engineer choices on 2026-10-12 remain within the owner's delegation and settled #2/#4 rules. `Subtask` persists exactly id/taskId/text/order/isCompleted, with UUID v4 identities checked against all currently implemented list/task/subtask records. `DatabaseProvider.getSubtaskRepository()` uses the shared database. Child text uses the same strict Unicode scalar/White_Space validation as task/list labels; original internal text remains. New children are unchecked, append at zero-based count, and cannot target a nonexistent task. Edit/check/reorder retains ID and parent identity. No separate subtask timestamps/reminders or incomplete search shadows are invented.

Per-parent reorder requires exactly that parent's full ID permutation once, rejects another parent's child, and moves through disjoint temporary positions inside one transaction to avoid the unique `(taskId, order)` index. Deletion compacts survivors to 0..N-1. Read/edit/check/delete of an unknown child or read/create/reorder of an unknown parent raises NoSuchElementException; invalid text/permutation/completion-gate operations raise IllegalArgumentException. SQLite failures propagate and roll back. Duplicate child text is allowed; independent parents/check states are retained.

TaskRepository.complete and every non-null setCompletion path check that no unchecked children exist in the same Room transaction as the completion write, including idempotent complete calls. A mixed checklist blocks parent completion without modifying children. Fully checked or no-child parents can be explicitly completed; checking the final child never auto-completes. Reopen clears both fields and preserves date/check states. Adding an unchecked child or changing a checked child to unchecked under a completed parent writes the child and reopens the parent in one transaction; requested date/time, other checked states and original task content/identity are retained. Existing Task active/completed observers invalidate after that commit. Text/order edits and child deletion leave parent completion instant/captured day unchanged. Example: parent A/B checked and completed Oct 12; uncheck A => parent unfinished, both completion fields null, B still checked, date/reminder unchanged. Delete the last unchecked child from an unfinished parent => completion becomes permissible but remains manual. Delete a child from a completed parent => parent remains completed on its original captured day.

Subtask.taskId is FK ON DELETE CASCADE. Parent deletion therefore removes its children in the same SQLite transaction; custom-list deletion already deletes tasks before its parent list, so children cascade with it. Unrelated parents/children survive. No app-level loop or no-op cascade layer is needed. Failed child insertion/check followed by failed parent reopen rolls back both; failed list removal after cascades restores child/task/list rows and order. Series/prototypes/one-occurrence overrides (#12/#13), checklist UI (#18), completed-day visibility (#11), confirmation (#27), OS/durable reminder integration (#28/#30), and full Unicode search caches (#26) stay deferred.

Explicit registered 3-to-4 migration adds only the subtask table/FK/unique owner-order index and retains list constraints; earlier Settings/list/task rows and generated schemas 1–3 are unchanged. Full 1-to-2-to-3-to-4 chain is retained. Actual exported-schema migration, further writes/reopen, completion gates/observers and rollback evidence are in [issue #8 validation](task-8-validation.md). No new dependency was required by this issue.
