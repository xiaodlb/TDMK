# Room storage foundation

Issue [#5](https://github.com/xiaodlb/TDMK/issues/5), following the full [local contract](data-model.md). Technical choices below were made by the Engineer on 2026-10-12 under the owner's delegation, within the PM-approved foundation scope.

## Implemented subset and initialization

Room version 1 implements only `settings`: its local primary key is the fixed singleton `id=1`, and `appearance` stores exactly `system`, `light`, or `dark` as TEXT. The local key is not a portable backup field or a globally generated domain-record UUID. The first successful creation inserts `system` in SQLite's creation transaction. Later opens do not insert/reset settings. The typed converter rejects unknown persisted appearance values; the DAO exposes read and atomic update of the existing singleton, with no insertion/deletion API. Settings stays in the same transactional database as future domain data, enabling later atomic restore. Example: select Dark, close/restart, read `id=1, appearance=dark`; the installation default does not overwrite it. No appearance UI is introduced by this issue.

Lists/default Inbox remain #6; tasks #7; subtasks #8; notes/formatting #9; recurrence/templates/exclusions #12. LocalWork and detached reminder safety storage remain with recurrence/reminder/restore implementation; search cache metadata stays with search. Those complete-contract requirements remain mandatory. Adding lists does not require implementing unseen task repositories first.

The manifest registers `TdmkApplication`. Its lazy `databaseProvider` uses the application context and stable private filename `tdmk.db`; creating the provider does not open SQLite. An application caller obtains the shared instance through `databaseProvider.getDatabase()` on a worker thread. Synchronized access opens/validates SQLite before publishing exactly one Room instance for concurrent/repeated callers. Callers must not construct additional providers for production access, close the database directly, or access SQLite from Compose; future state/repository code obtains the Application dependency. Tests use isolated filenames through the same provider/opening policy. The owner may close the provider only after all users stop; a later access reopens it.

Initialization failures propagate to the caller with their original type/message/cause; failed instances are closed and never cached as successful. An incompatible schema/version, unsupported downgrade, inaccessible file, I/O error or corruption must be reported, with the file retained for diagnosis and retry. There is no delete/recreate, alternate filename, in-memory replacement, swallowed error, destructive migration or data-loss recovery. A preserving open-helper factory delegates normal Room callbacks but replaces the framework corruption callback (which otherwise deletes files) with an exception, and disables `allowDataLossOnRecovery`. Example: a newer database with `user_version=2` cannot be opened by version 1: callers receive the missing 2-to-1 migration error, and its sentinel records/version remain readable. Corruption cannot promise readable records, but the original bytes are retained; the application must not claim a successful open. A full recovery screen is outside this issue.

## Version ownership and future migrations

`@Database(version=...)` in `TdmkDatabase` owns the Room/SQLite `user_version`. The Room Gradle plugin exports generated schemas to `app/schemas/com.xiaodlb.tdmk.data.TdmkDatabase/<version>.json`. Commit each generated version; retain every historical schema unchanged. Room schema 1 is this subset, independently of logical backup version 1 and `tdmk.blocks` rich-note version 1.

Every later table addition or existing schema change increments the Room version and supplies an explicit non-destructive `Migration(N, N+1)` registered in `DatabaseProvider` before release. The chain is presently empty because no previous released version exists. Example: #6 can add lists in 1-to-2 while leaving the existing Settings row/value untouched; #7 then adds tasks in 2-to-3, preserving both. Support all prior released versions by retaining/ registering the complete 1-to-2-to-3 chain; never replace 1.json or relabel a changed schema as version 1. An explicit verified direct migration is permissible only if it preserves equivalent state. Do not introduce a fake version-2 production table here just to test an upgrade.

Each migration's own implementation issue must exercise real exported old schemas with representative rows, run Room schema validation, and assert old IDs/content/settings survive before and after further writes/reopen. Upgrades may rebuild derived caches but preserve the full contract's user data, identities, ownership and safety state. Unknown versions, unavailable paths and downgrades fail safely; no downgrade migrations or destructive fallback are configured. #36 covers broader upgrade regression across implemented versions. This issue demonstrates preservation on reopen and rejected incompatible opens, not a successful migration to a nonexistent next version.

## Pinned tooling and primary guidance

- [Room releases/setup](https://developer.android.com/jetpack/androidx/releases/room): runtime/compiler/plugin **2.8.5**; Kotlin processing uses KSP, minSdk 23 matches this app, and the Room plugin's minimum AGP is 8.4. The plugin manages versioned schema export inputs/outputs.
- [AGP 9.0 release guidance](https://developer.android.com/build/releases/agp-9-0-0-release-notes): existing AGP **9.0.1** supplies KGP **2.2.10**. [Built-in Kotlin migration](https://developer.android.com/build/migrate-to-built-in-kotlin) recommends KSP over incompatible Kotlin kapt.
- [KSP 2.3.1 release](https://github.com/google/ksp/releases/tag/2.3.1) added AGP 9/built-in Kotlin support; pinned **2.3.6** retains that support and [fixes Windows KSP2 recompilation](https://github.com/google/ksp/releases/tag/2.3.6). AGP's older minimum 2.2.10-2.0.2 is insufficient for its source-set restrictions: the initial check failed configuration, then the pin was corrected. No restriction-suppression flag, separate Kotlin Android plugin, Kotlin toolchain upgrade or kapt is applied.
- [AndroidX Test releases](https://developer.android.com/jetpack/androidx/releases/test): runner **1.7.0**, JUnit extension **1.3.0**, only device-test dependencies.
- [Room migration policy](https://developer.android.com/training/data-storage/room/migrating-db-versions) and [SupportSQLiteOpenHelper callback](https://developer.android.com/reference/androidx/sqlite/db/SupportSQLiteOpenHelper.Callback) describe migration validation and the default corruption handler's deletion behavior.

Actual build/device results and reproduction commands are in [issue #5 validation](task-5-validation.md). Testing/design-system guides remain absent; existing project guidance applies. No task/note/reminder/backup/network feature or physical-phone result is claimed here.
