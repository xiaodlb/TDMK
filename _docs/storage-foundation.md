# Room storage foundation

Issue [#5](https://github.com/xiaodlb/TDMK/issues/5), following the full [local contract](data-model.md). Technical choices below were made by the Engineer on 2026-10-12 under the owner's delegation, within the PM-approved foundation scope.

## Implemented subset and initialization

Room version 1 implements only `settings`: its local primary key is the fixed singleton `id=1`, and `appearance` stores exactly `system`, `light`, or `dark` as TEXT. The local key is not a portable backup field or a globally generated domain-record UUID. The first successful creation inserts `system` in SQLite's creation transaction. Later opens do not insert/reset settings. The typed converter rejects unknown persisted appearance values; the DAO exposes read and atomic update of the existing singleton, with no insertion/deletion API. Settings stays in the same transactional database as future domain data, enabling later atomic restore. Example: select Dark, close/restart, read `id=1, appearance=dark`; the installation default does not overwrite it. No appearance UI is introduced by this issue.

Issue #6 adds lists/default Inbox in schema 2 as described below; issue #7 adds ordinary tasks in schema 3, issue #8 adds subtasks in schema 4, issue #9 adds independent formatted notes in schema 5, recurrence/templates/exclusions #12. LocalWork and detached reminder safety storage remain with recurrence/reminder/restore implementation; search cache metadata stays with search. Those complete-contract requirements remain mandatory. Adding lists does not require implementing unseen task repositories first.

The manifest registers `TdmkApplication`. Its lazy `databaseProvider` uses the application context and stable private filename `tdmk.db`; creating the provider does not open SQLite. An application caller obtains the shared instance through `databaseProvider.getDatabase()` on a worker thread. Synchronized access opens/validates SQLite before publishing exactly one Room instance for concurrent/repeated callers. Callers must not construct additional providers for production access, close the database directly, or access SQLite from Compose; future state/repository code obtains the Application dependency. Tests use isolated filenames through the same provider/opening policy. The owner may close the provider only after all users stop; a later access reopens it.

Initialization failures propagate to the caller with their original type/message/cause; failed instances are closed and never cached as successful. An incompatible schema/version, unsupported downgrade, inaccessible file, I/O error or corruption must be reported, with the file retained for diagnosis and retry. There is no delete/recreate, alternate filename, in-memory replacement, swallowed error, destructive migration or data-loss recovery. A preserving open-helper factory delegates normal Room callbacks but replaces the framework corruption callback (which otherwise deletes files) with an exception, and disables `allowDataLossOnRecovery`. Example in the current schema: a newer database with `user_version=6` cannot be opened by version 5: callers receive the missing 6-to-5 migration error, and its sentinel records/version remain readable. Corruption cannot promise readable records, but the original bytes are retained; the application must not claim a successful open. A full recovery screen is outside this issue.

## Version ownership and future migrations

`@Database(version=...)` in `TdmkDatabase` owns the Room/SQLite `user_version`. The Room Gradle plugin exports generated schemas to `app/schemas/com.xiaodlb.tdmk.data.TdmkDatabase/<version>.json`. Commit each generated version; retain every historical schema unchanged. Room schema 1 is this subset, independently of logical backup version 1 and `tdmk.blocks` rich-note version 1.

Every later table addition or existing schema change increments the Room version and supplies an explicit non-destructive `Migration(N, N+1)` registered in `DatabaseProvider` before release. The current registered chain is 1-to-2-to-3-to-4-to-5: #6 adds lists, #7 adds ordinary tasks, #8 adds subtasks, #9 adds independent notes while preserving earlier rows. Support all prior released versions by retaining/registering the complete chain; never replace 1.json or relabel a changed schema as version 1. An explicit verified direct migration is permissible only if it preserves equivalent state.

Each migration's own implementation issue must exercise real exported old schemas with representative rows, run Room schema validation, and assert old IDs/content/settings survive before and after further writes/reopen. Upgrades may rebuild derived caches but preserve the full contract's user data, identities, ownership and safety state. Unknown versions, unavailable paths and downgrades fail safely; no downgrade migrations or destructive fallback are configured. #36 covers broader upgrade regression across implemented versions. Historical #5 demonstrates preservation on reopen/rejected incompatible opens; #6 additionally checks the actual 1-to-2 upgrade.

## Lists in schema 2 (issue #6)

Engineer choices on 2026-10-12 under the existing delegation: `lists` persists the contract's id/name/isDefault/order/createdAt/updatedAt. IDs are cryptographically random UUID v4 strings, retained on edits; timestamps use the contract's SQLite INTEGER epoch-millisecond encoding and valid year range. The repository accepts an injectable millisecond clock, stores creation/update equally at creation, uses max(previous update, now) on changed content/order, and leaves timestamps unchanged on unchanged saves/permutations. No incomplete search shadow is invented; the original name is retained for later #26 integration.

`DatabaseProvider.getDatabase()` initializes the default through `ListRepository.initialize()` after schema validation and before publishing the opened instance. A single Room transaction finds the default flag or inserts Inbox with a new stable ID/order 0; reopening or concurrent initialization finds that same row even after rename. `getListRepository()` obtains the already shared database. Use the repository on worker threads; internal DAO mutations support its transactions. Schema 2 has a unique order index; two SQLite triggers enforce uniqueness of true default flags while allowing every custom flag to be false. These custom triggers are installed on creation and by 1-to-2 migration; Room exports table/index structure and ignores triggers, so retain their definitions in `ListSchema` across later migrations.

Names validate the exact Unicode White_Space set, trim only their edges, reject empty/whitespace-only strings and unpaired surrogates, and preserve internal text/whitespace. Duplicate names are allowed. Example: NBSP + `Work  🌿` + narrow NBSP becomes `Work  🌿`; a second identically named custom list has its own ID. Inbox rename to General preserves its flag/ID/order 0; default deletion is rejected before and after rename, retaining the owner's explicit rename selection and delegated deletion protection.

CRUD reads return persisted rows; create/rename return the saved row; reorder/delete return the resulting ordered rows. Unknown IDs raise `NoSuchElementException`; invalid names/permutations/default deletion raise `IllegalArgumentException`; SQL/storage failures propagate. Invalid requests cause no writes. Reorder requires the complete current custom-ID permutation exactly once, reserves disjoint positions within a transaction to avoid unique-index collisions, then assigns 1..N while keeping default 0. Deleting a custom list and compacting survivors is one transaction; a new custom list appends. Example: custom A/B/C reordered C/A/B remain 1/2/3 after reopen; delete A produces C/B at 1/2, adding D appends at 3. SQL-trigger failure after an early mutation rolls back every row/timestamp/order.

The 1-to-2 migration only creates the list table, unique-order index and default-uniqueness triggers. It never rewrites Settings or schema 1. After migration Room validates the schema, then the shared provider initializes Inbox. The generated-schema migration test sets Dark in exported version 1, validates version 2, confirms Dark, creates a list/updates appearance and verifies identity/state after reopening.

At delivery of #6, deletion handled list rows only. Issue #7 now deletes ordinary tasks before their custom list in that same transaction; task deletions now cascade through #8 subtasks; series storage is still pending. The mandatory final transaction must compute/delete a custom list's tasks and subtasks (#7/#8), stop owned templates and remove their occurrences including moved overrides, revisions and exclusions (#12), then remove the list, preserving unrelated other-list records and required detached reminder safety identities. SQL FK RESTRICT prevents premature parent removal when those relationships exist. Their migrations/repositories must extend this same transaction and test populated deletion before #21 exposes the confirmation UI, including moved occurrences in other lists. OS alarm/notification cancellation follows commit with durable retry work in its feature scope. No speculative callback/no-op cascade or claim of unimplemented cascade validation is added here. See [issue #6 evidence](task-6-validation.md) and [ordinary-task storage](task-storage.md) for the current #7 integration.
