## Goal

Document the local data model for TDMK in `_docs/data-model.md` so an engineer can implement its offline Room/SQLite storage without guessing field meanings, relationships, or lifecycle rules. Cover tasks, lists, subtasks, independent formatted notes, settings, and recurring templates with their occurrences; do not implement storage or cloud sync.

## Acceptance criteria

- [ ] `_docs/data-model.md` contains an entity/relationship diagram or table covering lists, tasks, subtasks, notes, settings, and recurring templates; each relationship states its cardinality and ownership, and notes have no relationship to tasks.
- [ ] Every persisted field has a name, type/encoding, nullability, default or an explicit statement that it has no default, and validation rule; the tables cover list order, task title/list/date/priority/short note/reminder/completion, subtask text/order/completion, note title/body/search text/timestamps, and the agreed settings and recurrence metadata.
- [ ] The document specifies stable-ID generation and uniqueness, Inbox identity, foreign-key behavior, and any uniqueness constraints; an occurrence has a documented identity that prevents generating it twice for the same template and scheduled date.
- [ ] Scheduled dates, reminder times, and completion/creation/update timestamps each have a stated representation and timezone interpretation; examples show an undated task, a dated task without a reminder, a dated task with a reminder, completion across midnight, and travel to another timezone without changing a date-only task's scheduled day.
- [ ] A lifecycle table states what is stored or derived for active, overdue, completed-today, historically completed, reopened, and deleted tasks; it includes subtasks and the behavior when a populated list is deleted, and does not require a midnight database move.
- [ ] Recurrence tables distinguish templates from occurrences and contain enough metadata to resume generation after an app restart; examples cover an unfinished previous occurrence, replayed reconciliation, a missed interval, a monthly date absent from a month, and occurrence-versus-series edits/deletions using the rules agreed in #2.
- [ ] The note contract names its versioned formatting representation, plain-text search/preview representation, and policy for invalid or unsupported format versions; examples include an empty body, bold text, headings, bullet lists, and Unicode, with no images or attachments.
- [ ] A schema/format-versioning section identifies what is versioned and documents how existing IDs, relationships, completion timestamps, and note formatting are preserved during future schema changes; stable local IDs do not require accounts or server IDs.
- [ ] An annotated example dataset contains Inbox, a custom list, an undated task, a dated task with a subtask and reminder, a completed task, a recurring template with two distinct occurrences, a formatted note, and settings; every field and reference matches the documented tables.
- [ ] The document links the scope and the completed decision record from #2 and #3; its behavior-sensitive rules match those decisions, and no implementation-blocking default, deletion policy, recurrence rule, or note-format choice is left as an unexplained TODO.
