## Goal

After the offline first version is established, document the requirements and compatibility contract for optional accounts and cloud sync. Identify the local-data changes a future sync implementation would need without implementing a backend or changing the first-version scope.

## Acceptance criteria

- [ ] `_docs/sync-contract.md` describes opting in from an existing offline dataset, signing out, account switching, and continued offline use, with owner-approved decisions clearly identified.
- [ ] A scenario table covers simultaneous edits, delete-versus-edit conflicts, recurring-occurrence duplicates, and a device reconnecting after a long offline period; each row states the agreed result or the specific decision still needed before implementation.
- [ ] A compatibility table states whether the local IDs, schema versions, relationships, and note format documented by #4 need additional sync metadata, with reasons and no speculative changes to the offline application.
- [ ] The document names the remaining backend/authentication decisions and links separate implementation issues for any agreed future work; no backend is chosen without recording its rationale and approval from the owner.

## Out of scope

- First-version local data modeling remains in [#4](https://github.com/xiaodlb/TDMK/issues/4).
- Offline backup export and restore remain in [#32](https://github.com/xiaodlb/TDMK/issues/32) and [#33](https://github.com/xiaodlb/TDMK/issues/33).
- Backend, authentication, and sync implementation are not part of this documentation task; create linked follow-up issues when their scope is agreed, rather than silently dropping requirements.

## Constraints

- Post-v1 planning task, not a prerequisite for shipping the offline application; read the completed `_docs/data-model.md` from #4 before starting.
- Changes stay in `_docs/sync-contract.md` and necessary guidance links. Do not write application code, add dependencies, provision services, or alter offline behavior.
- Follow `_docs/plan.md`, `AGENTS.md`, `_docs/process.md`, and `_docs/team/pm.md` on the project branch. Ask the owner one question at a time for unresolved product decisions.
