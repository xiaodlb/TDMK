## Goal

Provide a versioned Room database foundation that opens and reopens reliably without discarding local user data. Establish shared application wiring and safe initialization for incremental implementation of the documented local model, without implementing the downstream domain repositories.

## Acceptance criteria

- [ ] Room and compatible code-generation tooling are configured with pinned versions verified against current official compatibility guidance for the existing AGP 9.0.1/Kotlin 2.2.10 toolchain; `:app:assembleDebug` and existing local unit tests pass, and targeted instrumentation compiles and runs.
- [ ] Database initialization and dependency wiring provide one shared database instance per application process, using application context and a stable on-disk filename, with no database open in Compose screen code. A targeted check exercises repeated/concurrent access through that wiring and shows the same instance; actual initialization/open errors are observable to the application caller, not swallowed or replaced with a fresh/in-memory database.
- [ ] A generated, exported Room schema exists for the initial database version and is tracked, matching the implemented foundation subset of `_docs/data-model.md`. Document schema-version ownership and an explicit non-destructive migration chain for each later schema addition/change, distinct from logical backup/rich-note versions; no destructive fallback, delete-and-recreate, or unsupported downgrade is configured. Existing exported versions must remain available for later migration verification.
- [ ] A real on-disk persistence instrumentation check runs on the available Android API 36 phone/emulator and records device/API, command, report and assertions: create/open, write representative state through the foundation's actual persisted model subset, close, reopen the same filename, and read exactly the same values/identity without reset. Verify a subsequent write is readable after another reopen; an in-memory database, arithmetic test, source inspection, or open-with-no-data assertion alone does not satisfy this criterion.
- [ ] A targeted API 36 instrumentation case attempts an actual open of an isolated incompatible-version/schema fixture through the same initialization policy, observes a clear failure, and verifies the original sentinel data/version remain readable without silent deletion/replacement. The documented policy covers both incompatible and other open failures, preserves the file for diagnosis/retry, and does not claim a successful database open; no full recovery UI is required in this foundation issue.
