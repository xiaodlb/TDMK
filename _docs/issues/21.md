## Goal

People can create, rename, reorder, and delete lists from the final Tasks tab. Deletion makes the full effect on tasks and recurring series clear before records are removed.

## Acceptance criteria

- [ ] The final `Manage lists` Tasks tab opens a management view with the current default list first and custom lists in saved order. It exposes Create, Rename, and Reorder for custom lists, Rename for the default list, and Delete only for custom lists. With no custom lists, the default list and Create action remain available.
- [ ] Creating a valid list appends its custom tab and retains its stable ID after navigating away and restarting offline. Renaming either kind of list updates its row and Tasks tab without changing task ownership, ID, default role, or order. Quick entry from a date view still targets the renamed default list.
- [ ] Names use the existing `Label` contract: trim Unicode whitespace at the edges, preserve internal whitespace, reject blank/Unicode-whitespace-only and malformed Unicode input, and permit duplicates. Invalid Create or Rename shows a specific inline error, leaves stored data unchanged, and retains the entered text for correction. Cancel makes no write.
- [ ] Reorder controls move custom lists to every permitted position and visibly reflect saved order. The default remains at position 0; Today/Upcoming/Anytime stay first and Manage lists last. Order survives leaving Tasks, Activity recreation, and offline process restart. A failed reorder restores persisted order and offers retry without a partial move.
- [ ] Delete for any custom list, including an empty one, opens confirmation naming that list and explaining permanent removal of its tasks/checklists, owned recurring series and all their occurrences/overrides even in other lists, and exclusions. It also explains that occurrences of surviving series currently in the deleted list are removed and their original slots excluded. Empty-list copy may be simpler. No deletion occurs before explicit confirmation; Cancel/dismiss retains records and selection.
- [ ] Confirmed deletion removes affected records through the existing atomic repository operation and compacts custom order. Unrelated records survive. Example: deleting Work removes its series and an occurrence moved to Personal, but retains an unrelated Personal task; a Personal-series occurrence in Work is removed without regeneration. An injected failure leaves all lists, tasks, subtasks, series, exclusions, and order intact, shows an actionable error, and permits retry.
- [ ] The default list cannot be deleted before or after rename: Delete is absent and its repository guard remains. Deleting the selected custom list falls back to Today; subsequent quick entry uses the stable default-list ID. No stale deleted tab, row, or detail remains.
- [ ] Long names, many lists, portrait/landscape, and enlarged text keep Create, edit, reorder, Delete, confirmation, and Cancel reachable. Controls announce list names and action/state to accessibility services, show keyboard focus, and meet shared touch-target rules. A load failure shows Retry; pending writes cannot be double-submitted.
- [ ] Targeted checks cover valid/invalid/duplicate names and default rename, reorder positions and persistence, empty/populated deletion, cancellation, cross-list series effects and surviving-series exclusion, rollback, selected-tab fallback, offline restart, and enlarged-text/accessibility behavior. Record actual commands, device/API, tested commit, evidence, and unavailable checks in `_docs/task-21-validation.md`; independent QA checks every criterion before closure.
