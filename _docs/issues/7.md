## Goal

Store ordinary tasks and expose observable active/completed results to later screens.

## Acceptance criteria

- [ ] An ordinary task can be created with the #4 fields: stable UUID, existing/default list, title, optional date, Medium-default priority, nullable short note, optional reminder time, paired completion instant/captured local day, and creation/update timestamps. Every field survives on-disk reopening; date-only and minute-time encodings match the contract, null and empty short notes remain distinct, and IDs are unique across currently implemented lists/tasks.
- [ ] Updating each supported field retains task ID/creation time and follows the recorded update-time rule; observable consumers receive create/update/delete and completion-state changes without restarting. Verify changing list, retaining date-only values across timezone changes, preserving a completed task's captured completion day on unrelated edits, and clearing reminder time when its date is removed. Completion-state persistence is supported without implementing the later completion-view controller.
- [ ] Active and completed observable queries partition records by stored completion state, expose every matching record without purging history, and update after persisted changes. Capture completion instant/day together and clear them together for an unfinished record; priority/date-view filtering, completed-today crossing-out and Log eligibility remain #10/#11, not hard-coded into these persistence queries.
- [ ] Blank/Unicode-whitespace-only or invalid-Unicode titles, invalid priorities/dates/times, unpaired completion fields, reminders without dates, and nonexistent list IDs are rejected according to the contract without a partial write; title-edge trim preserves internal spaces. Default-list selection uses its stable flag after Inbox rename; task/list relationship is enforced with the documented RESTRICT foreign key, not orphaned records.
- [ ] Task deletion removes its ordinary-task record/short note/completion metadata; unknown-ID read/update/delete results are explicit and checked. Now that tasks exist, custom-list deletion atomically deletes its tasks before the list and compacts list order, while renamed default-list protection remains; an injected transaction failure preserves tasks/list/order. Subtask cascades (#8), recurring slots/exclusions/series (#12), confirmation (#27/#21), and reminder cancellation/safety work (#28/#30) remain linked integrations before those features are exposed, without claiming nonexistent dependent behavior tested.
- [ ] A targeted real Android API 36 on-disk persistence report covers create/update/delete/reopen, reactive-query updates, invalid-write and list-deletion rollback, and distinct dated/undated/completed records. Add/register a non-destructive Room 2-to-3 migration, track schema 3 while retaining 1/2, and use exported old schemas to verify Settings plus list IDs/names/order survive upgrade and subsequent task writes/reopen; retain the 1-to-2-to-3 path. Run existing foundation/list/local checks and debug build, recording device/API/commands/results without requiring account/network for app behavior.
