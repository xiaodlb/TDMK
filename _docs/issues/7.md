## Goal

Store ordinary tasks and expose observable active/completed results to later screens.

## Acceptance criteria

- [ ] A task can be created with title, existing list, optional date, priority, short note, reminder metadata, and completion timestamp; every field survives database reopening.
- [ ] Updating any supported field retains the stable task ID and observable consumers receive the saved result without reopening the application.
- [ ] Active and completed queries expose the stored records without losing completed history; date-specific visibility remains separate domain logic.
- [ ] Blank/invalid titles, invalid priorities, reminders without dates, and nonexistent list IDs are rejected according to the contract without a partial write.
- [ ] Deleting a task removes its record and respects the documented relationship policy; repository behavior for an unknown ID is explicit and checked.
- [ ] A targeted persistence report covers create/update/delete/reopen and confirms dated and undated tasks remain distinct.
