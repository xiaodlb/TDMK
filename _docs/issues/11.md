## Goal

Persist completion times and derive same-day crossed-out visibility and older completion history without a midnight database move.

## Acceptance criteria

- [ ] Completing a task stores its paired completion instant/captured current-device local day and makes it completed in domain results. Repeating complete while already completed retains the original pair and identity, with no duplicate record or changed timestamp; all command paths retain #8's unchecked-subtask gate and failure atomicity.
- [ ] For a fixed local day, same-day completions remain marked completed in their applicable active date/list results; older completionDate<today records appear only in history. Reuse #10's eligibility boundary, including completionDate>today after backward clock/day jumps. Home's overdue/today dated section retains eligible formerly-overdue same-day completions without changing #10's unfinished-only overdue classification; undated tasks remain in list/Anytime, not Home's dated sections.
- [ ] History groups use captured completionDate descending, then High/Medium/Low, createdAt ascending and ID ascending within each group, regardless of originally scheduled date. Historical records occur once, with no completed-today/future-day/reopened/deleted entries; examples cover two completion days and equal-priority/timestamp ties.
- [ ] Reopening clears both completion fields, preserves task ID/date/reminder metadata and every subtask state, and removes the record from history immediately. Existing observable stored candidates yield the appropriate overdue/today/upcoming/list/Anytime results; completing again captures a new pair/day, not a second task/history copy. Unchecking/adding an unchecked child still atomically reopens under #8.
- [ ] Focused deterministic checks/report cover completion at local 23:59:30 and 00:00:30, next-day evaluation/restart, forward/backward clock/day changes, and timezone travel without rewriting captured completion day or date-only schedule. A targeted real API 36 persistence check covers complete/repeat/reopen/recomplete and subscribed candidate updates, plus persistence through database reopen; run relevant existing tests/debug build and record commands/device/results.
- [ ] History/active visibility derives from the same stored records and captured day plus an explicit controllable clock; next-day evaluation needs no write, purge, separate Log table or midnight background move. Reuse existing schema 5 and #10 ordering/eligibility instead of introducing another storage model.
