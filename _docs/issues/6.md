## Goal

Persist custom task lists and their order, with exactly one stable default Inbox.

## Acceptance criteria

- [ ] Create, read, rename, reorder, and delete operations return persisted results matching the list contract in _docs/data-model.md: stable UUID identity, trimmed Unicode nonblank name, default flag, contiguous order and creation/update timestamps. The repository uses the shared database wiring from #5 and documents unknown-ID/invalid-operation results without partial writes.
- [ ] First initialization creates exactly one Inbox at order 0; repeated/concurrent initialization and application/database reopening preserve its ID and never create another. Initialization after upgrading an existing Settings-only version-1 database adds that default without resetting its Settings value; do not identify it by its mutable name or replace it on each open.
- [ ] Three custom lists retain their IDs, names and reordered positions 1..3 after closing and reopening the on-disk database. Reorder accepts a complete permutation of current custom IDs, keeps the default at 0, and rejects duplicate/missing/unknown IDs without changing order; deletion compacts surviving positions and adding another appends it.
- [ ] Inbox rename succeeds while preserving its stable default role, ID and position; deletion is rejected before and after rename. This preserves the explicit owner rename selection and delegated deletion protection from #2. Blank/Unicode-whitespace-only or invalid-Unicode names are rejected, name-edge trimming preserves internal whitespace, and duplicate list names remain allowed as specified by the contract.
- [ ] Custom-list deletion and reorder are atomic for the currently implemented list storage; a targeted transaction-failure case demonstrates unchanged prior records/order, with no partial deletion/reorder. Document the full relationship deletion policy and its linked future integration: task/dependent storage (#7/#8) and series/overrides/exclusions (#12) must join the same transactional deletion before populated-list deletion is exposed in #21. Do not implement nonexistent downstream entities or claim their cascade verification here.
- [ ] Real Android API 36 on-disk persistence/migration tests cover these operations offline, plus a generated-schema version-1-to-2 upgrade preserving a nondefault appearance setting, Room schema validation, and further writes/reopen. Track generated schema 2 without modifying schema 1, register the explicit non-destructive migration, run existing foundation/local checks and debug build, and record device/API/commands/results with no account/network requirement for application behavior.
